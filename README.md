# MaintBot

Telegram-бот для управления серверным сервисом: мониторинг, подписки, поддержка и уведомления в одном месте.
Пользователи получают доступ и персональные ссылки через бота, а сотрудники обрабатывают заявки и следят за серверами из Telegram.

## Что умеет бот

- **Мониторинг серверов.** Доступность, память и uptime узлов RemnaWave через `/metrics`, независимые DNS- и TLS-проверки. При прямом запуске на Linux также доступны локальные проверки диска, UFW, Docker и событий fail2ban.
- **Доступ и подписки.** Заявки на доступ, одноразовый тест, покупка и продление подписки, персональные ссылки подключения и напоминания об оплате.
- **Поддержка.** Тикеты с текстом, фотографиями и документами. Скриншот можно отправить как обычную фотографию с подписью или без неё при создании тикета и в ответе. При открытии тикета или нажатии «Показать вложения» бот повторно отправляет сохранённые вложения пользователя и администратора. Сотрудники могут брать обращения в работу, передавать коллегам, закрывать и архивировать их.
- **Техработы.** Немедленный или запланированный запуск, выбор серверов, продление и завершение работ с уведомлениями пользователей. Ответственным сотрудникам приходит одно напоминание, если работы продолжаются после заявленного срока простоя; продление задаёт новый срок.
- **Администрирование.** Управление пользователями и сотрудниками, личные сообщения, рассылки всем пользователям или только администраторам, настройка реквизитов и цены, выгрузка клиентов в XLSX.

## Как устроена работа

### Для пользователя

Знакомство с ботом начинается с `/start` и заявки на доступ. После одобрения пользователь может обратиться в поддержку,
запросить тест или купить подписку. Персональная ссылка находится в разделе подписки; её можно открыть или добавить в Happ.
В профиле можно сохранить резервную электронную почту.

Оплаченная подписка также открывает просмотр состояния серверов. Бот напоминает о продлении за три дня, за день
и за 15 минут до окончания. Если оплата следующего периода не подтверждена, пользователь возвращается на базовый
уровень и получает уведомление с возможностью снова купить подписку или обратиться в поддержку.

### Для сотрудников

Администратор входит командой `/auth <пароль>`. Команда `/owner <пароль>` назначает единственного руководителя сервиса.
Остальные действия доступны через кнопки меню.

| Должность | Основные права |
| --- | --- |
| Специалист поддержки | Работа с пользователями, тикетами и заявками, выдача стандартного теста, отправка реквизитов |
| Инженер сопровождения | Дополнительно — управление техработами |
| Ведущий инженер сопровождения | Дополнительно — массовое изменение дат подписок и напоминания об оплате |
| Руководитель сервиса | Настройки оплаты, подтверждение платежей, произвольный срок теста и выгрузка клиентов |

Права сотрудника и пользовательская подписка учитываются отдельно. У руководителя — бессрочный оплаченный доступ.

## Подписки и оплата

Руководитель задаёт стандартную цену, реквизиты и даты платёжных периодов в разделе
«Администрирование → Настройки сервиса». По умолчанию тариф составляет 300 ₽ за три месяца.
Также предусмотрен безлимитный тестовый доступ без оплаты и даты окончания.

Покупка проходит в несколько шагов:

1. Пользователь создаёт заявку на подписку.
2. Администратор проверяет её и отправляет реквизиты.
3. Пользователь переводит деньги и нажимает «Я оплатил».
4. Руководитель подтверждает поступление, после чего бот активирует подписку до указанной даты.

В разделе «Заявки» сотрудники могут переключаться между активными заявками и архивом.
Архив содержит одобренные, отклонённые и отменённые заявки на тест, покупку и продление;
их карточки доступны для просмотра. Оба списка имеют постраничную навигацию.

Перед отправкой реквизитов в заявке можно нажать **«Цена и срок»** и назначить индивидуальные условия:

```text
500 | 2
500 | 2 | 31.12.2026 23:59
```

Первый вариант означает 500 ₽ за два календарных месяца от момента ввода. Второй задаёт точную дату окончания
в часовом поясе бота. Сумма указывается в целых рублях, срок — в месяцах. Бот покажет условия для подтверждения.
Они действуют только для этой заявки: следующее продление использует актуальную стандартную цену.
После отправки реквизитов условия заявки фиксируются.

В тексте реквизитов доступны подстановки `{amount}`, `{months}` и `{access_until}` — сумма, число месяцев и дата окончания.
Используйте их вместо записанных вручную цены и срока, чтобы сообщение соответствовало заявке.

Стандартный одноразовый тест выдаётся на 24 часа. Другой срок может выбрать руководитель.
Для теста сотрудник назначает новую ссылку с таким же сроком действия во внешней панели.
В карточке пользователя можно отдельно посмотреть сохранённую ссылку, заменить её или отправить пользователю.

MaintBot учитывает оплаты и сроки, но не проверяет банковские переводы автоматически и не создаёт доступ в RemnaWave.
Создание, продление и отключение доступа во внешней панели выполняются отдельно.

## Установка в Docker

Бот и встроенная база SQLite работают в одном контейнере. Пользователи, подписки, заявки, тикеты,
очередь уведомлений, кэши и состояния диалогов сохраняются в `data/maintbot.sqlite3` на хосте.
Настройки оператора остаются в JSON, секреты хранятся отдельно от кода.
Telegram использует long polling: входящие порты и webhook не нужны.

Нужны Linux с Docker Engine и Docker Compose v2. Образ использует версию Python из [.python-version](.python-version)
и зависимости из [app/requirements.txt](app/requirements.txt). Контейнер запускается от UID/GID `10001`,
без привилегий, Docker socket и SSH-ключей. Файлы БД находятся на локальной файловой системе с корректной
блокировкой и синхронизацией; сетевые диски NFS/SMB требуют отдельной проверки.

### Перенос на Debian 13 с готовым образом

Для поставки уже собранного образа используйте режим `--image`:

```powershell
docker build --platform linux/amd64 -t maintbot:YOUR_VERSION .
.\.venv\Scripts\python.exe -m tools.prepare_deployment --panel-only --image maintbot:YOUR_VERSION --output release/offline
docker save -o release/offline/maintbot-image.tar maintbot:YOUR_VERSION
```

В этом режиме `compose.yaml` содержит указанное имя образа, `pull_policy: never` и не содержит
сборку из GitHub. Передайте архив образа и подготовленные Compose/data на сервер. Архитектура образа
должна соответствовать серверу (`linux/amd64` для `uname -m` = `x86_64`, `linux/arm64` для `aarch64`).
В примере выбран `linux/amd64`; для ARM-сервера замените платформу при сборке.
На сервере сначала загрузите образ, затем запустите сервис:

```bash
cd /opt/maintbot
sudo docker load -i maintbot-image.tar
sudo chown -R 10001:10001 data
sudo chmod -R u=rwX,go= data
sudo docker compose up -d
```

Однократная миграция разнесённых JSON и состояния Telegram выполняется штатным entrypoint образа.
Перед экспортом образа выполните оба аудита зависимостей из CI и проверьте версии внутри собранного
образа. Такая поставка включает локальные исправления и не зависит от их публикации в GitHub.

### Перенос на Debian 13 с удалённой сборкой

Этот способ подходит, когда прежнего сервера уже нет, а весь проект с `data/` и `app/env.secrets`
сохранился на компьютере. На сервер загружается только подготовленный каталог `release/`.
Docker сам получает исходники из ветки `dev` публичного репозитория и собирает образ.
Публиковать образ в registry или загружать исходники на сервер вручную не нужно.

На компьютере из корня проекта выполните:

```powershell
.\.venv\Scripts\python.exe -m tools.prepare_deployment --panel-only
```

На Linux тот же инструмент запускается через Python проекта:

```bash
.venv/bin/python -m tools.prepare_deployment --panel-only
```

Инструмент создаёт новый `release/`, сохраняя исходные данные и секреты без изменений:

```text
release/
├── compose.yaml
└── data/
    ├── conf/                       # Настройки, подготовленные для Docker
    ├── config-before-docker/       # Исходные настройки
    ├── env.secrets                 # Копия прежнего файла секретов
    ├── telegram-migration.pickle   # Выбранное состояние Telegram, если найдено
    └── ...                         # Полная копия прежнего data
```

Пути меняются только в копии конфигов. Ключи и UUID узлов сохраняются; `--panel-only` оставляет
узлы RemnaWave, исключает проверки хоста, отключает Docker/fail2ban и удаляет прежние настройки SSH.
Отчёт показывает число оставленных и исключённых узлов. Если настроенных узлов панели нет,
подготовка останавливается.
Выбранный pickle копируется отдельно, чтобы сохранить состояния диалогов при первом импорте.
Для нестандартных файлов доступны `--config-dir`, `--secrets-file` и `--ptb-pickle`.
Без `--image` используется описанный ниже сценарий удалённой сборки из опубликованного кода.
Существующий выходной каталог не перезаписывается; для новой копии укажите `--output release-new`.

`release/` содержит реальные данные и секреты и исключён из Git. Передавайте его по SSH/SFTP.
Загрузите **содержимое** `release/` в `/opt/maintbot` нового сервера:

```text
/opt/maintbot/compose.yaml
/opt/maintbot/data/
```

На Debian 13 нужен Docker Engine с плагином Compose. Установка из официального репозитория описана
в [инструкции Docker для Debian](https://docs.docker.com/engine/install/debian/).
После установки выполните на сервере:

```bash
cd /opt/maintbot
sudo chown -R 10001:10001 data
sudo chmod -R u=rwX,go= data
sudo docker compose up -d --build
sudo docker compose logs -f --tail=100 maintbot
```

Поддерживается только текущее разнесённое JSON-хранилище: в `data/` должны находиться
`storage_layout.json` и все перечисленные в нём файлы. Старые монолитные хранилища не импортируются.
При первом запуске Compose автоматически переносит разнесённые JSON и состояние Telegram в SQLite и сохраняет
checksum-проверенную копию источников в `data/sqlite-backups/`. Прежние JSON остаются на месте.
При следующих запусках используется `data/maintbot.sqlite3`; повторного импорта нет.
Если БД повреждена или исходные данные неполные, запуск останавливается, а пустая БД вместо них
не создаётся. Пустая новая установка инициализируется отдельно от ветки миграции.

Проверка конфигурации выполняется до запуска Telegram polling. После запуска убедитесь, что в боте
сохранились пользователи, права, подписки и тикеты; повторно назначать руководителя не нужно.
Первый запуск может отправить накопившиеся уведомления. Из-за смены транспорта пересоздайте
запланированные техработы отдельных серверов со старым fingerprint, если они были.
Первой сборке требуется исходящий доступ к GitHub, registry базового образа и PyPI; работающему
боту — к Telegram и панели. Входящие порты для бота не нужны.

Удалённая сборка использует опубликованную ветку `dev`; перед развёртыванием изменений отправьте
их в эту ветку. Чтобы закрепить проверенный полный commit, задайте `MAINTBOT_SOURCE_REF` для Compose.
Перед обновлением сохраните резервную копию и выполните `docker compose up -d --build`.
Ранее подготовленные папки и архивы поставки сохраняют старый Compose: создайте новую поставку
через `--output release-new`, чтобы использовать актуальный сценарий запуска.

### Локальная сборка из исходников

В каталоге проекта выполните:

```bash
sudo install -d -m 0700 -o 10001 -g 10001 data
sudo install -d -m 0750 -o "$(id -u)" -g 10001 conf conf/servers
cp examples/conf/docker-bot.json conf/bot.json
cp examples/conf/docker-server.json conf/servers/panel.json
cp app/env.secrets.example app/env.secrets
sudo chgrp -R 10001 conf app/env.secrets
chmod 0750 conf conf/servers
chmod 0640 conf/bot.json conf/servers/panel.json app/env.secrets
```

Заполните `app/env.secrets` по [примеру](app/env.secrets.example):

| Переменная | Назначение |
| --- | --- |
| `BOT_TOKEN` | Токен Telegram-бота от BotFather |
| `ADMIN_PASSWORD` | Пароль входа для администраторов |
| `OWNER_PASSWORD` | Отдельный пароль назначения руководителя |
| `REMNAWAVE_METRICS_USER`, `REMNAWAVE_METRICS_PASS` | HTTP Basic Auth для метрик панели, если требуется |

Административные пароли должны отличаться и содержать не менее 16 символов. Если метрики работают
без авторизации, оставьте обе переменные RemnaWave пустыми. Секреты и рабочие конфиги не входят в образ.

В `conf/bot.json` задайте часовой пояс и настоящий `REMNAWAVE_METRICS_URL` панели.
В `conf/servers/panel.json` замените `monitoring.node_uuid` на UUID нужного узла, укажите название сервера.
Для нескольких узлов создайте отдельные JSON-файлы с уникальными `key` и UUID. Порядок задаёт `display_order`.
При необходимости настройте внешние DNS- и TLS-проверки в `domains` по
[примеру сервера](examples/conf/servers/panel-example.json).

Docker-пример использует `connection.transport: "panel"` и `monitoring.source: "remnawave"`.
В этом режиме бот получает ресурсы и доступность узлов с панели; DNS и TLS проверяет по сети.
Disk/UFW, локальные метрики хоста, Docker и fail2ban недоступны;
старые значения этих проверок не отображаются. Список контейнеров должен быть пустым,
`fail2ban.enabled` — `false`. Эти параметры проверяются при загрузке конфигурации.

SSH-доступ к серверам, включая резервную проверку disk/UFW, удалён. Допустимые транспорты —
`panel` и `local`; в `connection` больше нет поля `target`. При обновлении вручную удалите
`SSH_STRICT_HOST_KEY_CHECKING`, `SSH_KNOWN_HOSTS_FILE` и `SSH_IDENTITY_FILE` из `bot.json`,
а `connection.target` — из файлов серверов. Прежние серверы с транспортом `ssh` переведите на
`panel` с UUID узла RemnaWave. Конфигурации без внешнего источника метрик требуют отдельной настройки
источника или удаления сервера из инвентаря. `tools.prepare_deployment` подготавливает копии
настроек для панели автоматически; исходные файлы сохраняются.

Пути внутри контейнера фиксированы примером развёртывания:

| Путь | Назначение |
| --- | --- |
| `/var/lib/maintbot` | Постоянный каталог БД и runtime lock; `DATA_DIR` |
| `/etc/maintbot/conf` | Настройки, подключённые только для чтения |
| `/run/secrets/maintbot.env` | Секреты, подключённые только для чтения |

`PTB_PERSISTENCE_PATH` оставьте пустым: рабочие состояния Telegram теперь находятся в той же SQLite БД.
`INSTANCE_LOCK_PATH` также оставьте пустым: блокировка создаётся внутри `DATA_DIR/runtime`.

### Запуск и обновление

```bash
docker compose build
docker compose up -d
docker compose logs -f --tail=100 maintbot
```

При первом запуске контейнер создаёт пустую БД, выполняет проверку конфигурации и запускает бот.
При следующих запусках использует существующую БД. Если найдены поддерживаемые JSON-данные без БД,
перед запуском автоматически выполняется однократная миграция с резервной копией.
Неполные исходные данные или повреждённая БД останавливают запуск.

Откройте чат с ботом, отправьте `/start`, затем `/owner <OWNER_PASSWORD>`.
В настройках сервиса задайте реквизиты, цену, даты периодов, контактную почту и текст помощи.

Для проверки и перезапуска после изменения конфигурации:

```bash
docker compose run --rm maintbot python -m app.config_check
docker compose restart maintbot
```

Для обновления кода снова выполните `docker compose build` и `docker compose up -d`.
`docker compose stop` даёт боту 90 секунд на штатное завершение и сохранение состояния.
Сервис должен работать в одном экземпляре; не запускайте одновременно systemd и контейнер с одним токеном.

Каталоги хоста можно изменить переменными Compose `MAINTBOT_DATA_DIR`, `MAINTBOT_CONFIG_HOST_DIR`
и `MAINTBOT_SECRETS_FILE`. Внутренние пути сохраняются. Локальный путь данных должен существовать
и быть доступен UID/GID `10001` для записи; конфиги и секреты — для чтения.

### Ручная проверка и перенос существующих данных

Если прежний бот ещё работает, остановите его. Сохраните отдельную резервную копию каталога данных.
Поместите старое хранилище в подключаемый каталог `data`, скопируйте операторские настройки из `data/conf`
в отдельный `conf` и замените пути в `conf/bot.json` значениями Docker-примера.
Для серверов включите транспорт `panel`, удалите `connection.target`, отключите fail2ban
и очистите `docker.containers`. Удалите прежние параметры `SSH_*` из `bot.json`.
Сохраните прежние `key` и UUID узлов. Обновление транспорта намеренно меняет идентичность мониторинга:
старые кэши и задания, привязанные к прежней конфигурации сервера, не должны переноситься на новую.

```bash
sudo chown -R 10001:10001 data
docker compose build
docker compose run --rm maintbot python -m app.persistence.migrate_sqlite --data-dir /var/lib/maintbot --dry-run
docker compose run --rm maintbot python -m app.persistence.migrate_sqlite --data-dir /var/lib/maintbot
docker compose up -d
```

Команда переноса проверяет исходное хранилище, сохраняет резервную копию и публикует БД только после
успешного переноса. Исходные JSON-файлы сохраняются для отката; дальнейшие изменения записываются в SQLite.
Стандартный старый файл `telegram/persistence.pickle` обнаруживается автоматически; для другого пути
передайте `--ptb-pickle /var/lib/maintbot/путь-к-файлу`. Импортируйте только свой доверенный pickle-файл.
При нестандартном пути блокировки прежнего процесса используйте `--instance-lock` и убедитесь,
что старый процесс остановлен. После запуска новой версии возврат к старым JSON без обратного переноса
теряет последующие изменения.

### Резервное копирование и восстановление

Остановите контейнер и копируйте весь каталог `data`, включая SQLite `-journal`, если он присутствует,
а также отдельно конфиги и секреты. Нельзя копировать только основной файл БД во время работы бота.
Для восстановления остановите сервис, восстановите согласованную копию каталога и права UID/GID `10001`,
затем выполните `docker compose up -d`. Данные сохраняются при пересоздании контейнера.

### Запуск без Docker

Прямой Linux/systemd-запуск остаётся доступен через [unit](deploy/maintbot.service) и `python -m app.launcher`.
Он также использует SQLite. [Обычный конфиг](examples/conf/bot.json) и
[пример локального сервера](examples/conf/servers/local-example.json) сохраняют проверки хоста.
Для локальных UFW/Docker/fail2ban нужен ограниченный [maintbot-helper](deploy/maintbot-helper)
с root-политикой и [sudoers](deploy/maintbot-sudoers). Внешние узлы подключаются через
[панель RemnaWave](examples/conf/servers/panel-example.json).
Добавлять контейнеру привилегии или монтировать Docker socket для режима панели не требуется.

## Команды в Telegram

Основные действия доступны через кнопки. Команды позволяют сразу открыть нужный раздел:

| Команда | Действие |
| --- | --- |
| `/start`, `/menu` | Главное меню |
| `/help` | Помощь |
| `/subscription` | Подписка и персональная ссылка |
| `/ticket` | Обращение в поддержку |
| `/health` | Состояние серверов в пределах доступного уровня |
| `/users` | Управление пользователями для администратора |
| `/fail2ban` | События fail2ban для администратора |
| `/maint` | Техработы для сотрудников начиная с инженера сопровождения |
| `/auth <пароль>` | Вход администратора; также доступна команда `/login` |
| `/owner <пароль>` | Назначение руководителя сервиса |
| `/logout` | Выход из текущей сессии |
| `/cancel` | Отмена текущего диалога |
